# 設定は user と project の2ファイルを順に重ねる

- 状態: 採用
- 日付: 2026-10-05
- 対象: 設定の保存先と解決規則

## 背景

スコープは Global と Project の2つが要求されています。候補は、ユーザーファイル1つにプロジェクトを絶対パスで格納する案、Pi 本体の settings に書き込む案、2ファイルを重ねる案でした。解決規則も、無効リストの和集合、4象限の対立モデル、逐次適用が候補でした。

## 決定

- Global は `<agent dir>/pi-switch.json`、Project は `<cwd>/.pi/pi-switch.json` に置きます。Project は信頼されたプロジェクトのときだけ読み書きします。
- 適用順は Global の `disabled`、Global の `enabled`、Project の `disabled`、Project の `enabled` です。各層の `enabled` はその層の `disabled` を打ち消し、後の層が常に勝ちます。
- どのリストにも無い対象は有効のままです。

## 理由

- 2ファイルは Pi 本体の settings と同じ場所・同じ精神で、ユーザーが既に知っている配置です。プロジェクトの設定はリポジトリへコミットできます。
- 逐次適用は「この層で無効、この層で有効」と読むだけで済み、無効リストの和集合ではできない「Global で無効にしたものを特定のプロジェクトだけ有効に戻す」を表現できます。4象限の対立モデルより規則が少ないです。
- パッケージの指定を各層のリストに置くことで、パッケージ一括と個別指定が同じ解決規則で扱えます。

## 帰結

- `/switch` の Project スコープは、未信頼プロジェクトでは編集できません。理由を画面に表示します。
- Project の設定をコミットする運用では、`npm:` パッケージのバージョン付き `sourceInfo.source`（例 `npm:pi-exa@1.2.3`）を正規化した `npm:pi-exa` で書きます。`npm:` 以外のソースは版を含む文字列のまま使います。
- 既存の4象限モデルの設定ファイルは読み込めません。pi-switch は新しい形式のため移行は不要です。

## 代替案

| 代替 | 却下理由 |
|---|---|
| ユーザーファイル1つにプロジェクトを絶対パスで格納する | プロジェクトの設定をリポジトリに置けず、マシン間で共有できない。パス移動で壊れる |
| Pi の settings（`defaultTools` や resource フィルタ）に書き込む | ツール用の設定キーが Pi に無い。拡張からの書き込み API も公開されていない。reload が必要 |
| 無効リストの和集合（有効への上書きなし） | Global で無効にしたものをプロジェクト単位で戻せない |
| 4象限の対立モデル | 逐次適用で同じ結果をより少ない規則で表せる |
